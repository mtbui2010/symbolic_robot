# Experiment protocol, step 3: a messy person

Written before the first full run (adapted to the factory domain only; the original also covered a household simulator, which is not part of this suite). Its sha256 is recorded in `<results dir>/PROTOCOL_SHA256` by `python -m bench run`; the file must not change after that.
Step 1 (`protocol.md`) used a scripted person who always names one clear place. Here the person is messy. Everything is **simulation**: a scripted person written for this repo, a simulated factory floor (mine), a single model (the LoRA reader serves every role). Nothing here is a claim about a real robot, a real plant or a real person.

## Question
When the person's answer is not one clear place, do the engine options that act on the answer (`ask_source_reask`, `relook`, `confirm_look`) help, and which kinds of messy answer does the robot handle at all?

## Engine, models, domains
As in `protocol.md`: engine `~/trung_workdir/robot_agent` (branch `live/no-ros`, working tree, not edited; its state is to be recorded in each results folder), Ollama model `hl-understand-p3-s700` for every role, profile `real` (detector miss 10 %, grip slip 5 %, drop 3 %, transient fault 2 % per call, persistent fault in 4 % of episodes; round numbers chosen by me, not measured). Domain: the **factory** (`assembly_hall`). The factory's ENV is the pack's (`symbolic_robot/domains/factory/configs/tasks.py`): each place has its name, "<name> in the <zone>", the id stem and the floor's own aliases. English only.

## Tasks (generated by `symbolic_robot/domains/factory/messy.py`, task seed 7, nothing hand-picked)
42 tasks: 6 for each of 7 answer policies, in rotation. Every task is "Put the X on D." (no source named; same pairing as `tasks_gen.generate_tasks`).
The wording is made from the world's own data: the place's name and aliases, the name of its room/zone, the head noun of its name, the other places' names. Sentence frames are fixed English frames written for this repo.

| policy | the person says (1st where-question) | 2nd where-question (and later) |
|---|---|---|
| `knows` (reference, step-1 policy) | the true place | the true place |
| `wrong` (reference, step-1 policy) | a real place where the object is not | the true place |
| `room_only` | only the room/zone: "It is somewhere in the tool crib." | the room again ("As I said, ...") |
| `vague` | no place: "Over there." / "Hmm, around here somewhere." / "I am not sure, maybe near the benches." (plural head noun of the true place's name) | "I told you, I am not sure." |
| `mind_change` | a wrong place ("I left it on the tool wall.") | "No wait, it is on the <true place>." |
| `partial_name` | the true place under a changed name, by one edit of the world's own names, in rotation: an alias of the floor/house data, an abbreviation of the longest word ("assem. bench 1"), a swap of two inner letters ("frigde"), or one word dropped (the one that leaves fewer other places that could match). A kind that does not apply to the name falls to the next kind; the kind and the number of other places the new name could mean are stored with the task | the full true name |
| `silent` | an empty string or "..." (alternating) | a true place ("Sorry. It is on the <true place>.") |

The last answer of a script repeats if the robot asks more often. The person's other answers are as in step 1: a destination question gets the destination, a confirmation "Yes.", "which" the object's name. An answer is **unusable** when it names no place (`room_only`, `vague`, `silent` first answers). No rule, probability or data of any other benchmark is used; no benchmark split is read.

## Arms (identical tasks, identical simulator seeds per task and repeat)
| arm | ask_source | ask_source_reask | search_route_weight | relook | confirm_look |
|---|---|---|---|---|---|
| A | 1 | 0 | 0 (old behaviour) | - | - |
| C | 1 | 1 | 0.3 | - | - |
| D | 1 | 1 | 0.3 | 1 | 1 |
| A2 | 1 | 0 | 0 (A repeated: noise of the whole pipeline) | - | - |

Options are sent as run options with every run (flat legacy names, which the engine accepts; they override the environment), so one server serves all arms. `-` = not sent, engine default (off). Per (task, repeat) the simulator seed is `task_number*100 + repeat` for all arms; 2 repeats (0, 1); arm order rotates with the task index; each episode starts with `reset_world` (objects in place, robot on its dock, object memory and run memory erased); timeout 420 s wall. Episodes: 42 x 4 x 2 = 336. One experiment process at a time.

## Measures (from the simulator's truth, not from the robot's claim)
* **success**: the goal object is at the destination place at the end. **wrong-done**: the engine says `done`/`success` and the truth says not.
* **distance**: metres travelled (straight legs of successful moves), from the simulator's call log.
* **questions**: questions the robot asked (listen events); `q_source`: where-questions about the object.
* **unusable answers**: answers of the person that name no place (counted per episode). **clarified**: unusable answers that were followed by another where-question. **clarify rate** = sum clarified / sum unusable answers, over episodes with at least one unusable answer.
* **fail reason**: the engine's own `done` message of a failed episode, put in a class by its text: `search gave up` ("could not find"), `grip or place fault` ("place failed", "slipped", "fell"), `goals do not hold` ("the goals do not hold"), `asked then stopped` (other text mentioning a question/answer), `other`; and `timeout`, `no done event`. Every episode also stores the simulator's injected faults from the call log (`faults`: drop, grip slip, detector miss, hardware fault...). Failed episodes whose log has a placement fault (`dropped`) are counted separately as **failed after a placement fault** in the report: that failure is the simulator's, not the answer's, but those episodes are NOT removed from any statistic.

## Analysis (`bench/suites/factory/analyze_messy.py`)
Unit: the task (measures averaged over the 2 repeats). Paired differences arm minus A (also A2 minus A for noise; D minus C as a secondary comparison): mean with a 95 % bootstrap interval (10000 resamples of tasks, seed 0). Sign test (exact, two-sided, ties dropped) on the **combined** per-task criterion of step 1: success rate higher = win, lower = loss; equal success: distance lower by more than max(0.5 m, 5 % of A's) = win, higher by more = loss. Also success-only and distance-only counts. Tables per arm and per policy, and the new measures.

**Pre-registered win rule** (evaluated on all 42 tasks): arm C or arm D beats A when it wins on more tasks than it loses on the combined criterion **and** the mean paired difference of wrong-done is not above 0. The rule is met when C or D beats A. It is reported as met or not met; evidence strength is the sign test p. A win is called **above noise** only if its wins minus losses is larger than |wins minus losses| of A2 vs A. No correction for the two comparisons.
The 30 tasks of the five new policies (without `knows`, `wrong`) are reported as a secondary subset with the same statistics.

**Per-policy reporting**: each policy has 6 tasks. The best possible exact sign test with 6 tasks is p = 0.031 (6 wins, 0 losses), 5/0 gives 0.0625. A policy-level win is claimed **only** if wins > losses and p < 0.05 for that policy and arm; otherwise the per-policy numbers are descriptive and are described as such (counts, means, and which episodes failed why). 14 per-policy tests are made (7 policies x 2 arms); no correction, so about one significant result is expected by chance alone and is not to be read as a finding unless the episodes show the mechanism. Which messy kinds the robot handles is judged from the episodes (success of A as well as of C and D, the questions asked, the fail reasons), and an engine problem is written down only with episode ids.

## Pilot and fixes
Before the full run, 10 tasks (two per new policy: t02 to t06, t09 to t13), arms A, C, D, 1 repeat, are run (60 episodes); every failure is read for bugs of my own (simulator, runner, wording generator). Fixed before the pilot ended: wording-generator defects found when reading the generated sentences (a plural "benchs", an abbreviation followed by two full stops, a letter swap that changed nothing in "toolbox"). The pilot (60 episodes) found no defect in the runner or in the simulator; the failures were genuine search give-ups (the robot does not use a room, a vague phrase or an abbreviation) and simulator faults (a placed object falling, a grip slip, a detector miss). Genuine robot behaviour or a simulator fault from the fault profile is reported, not patched. The engine is not edited. Pilot episodes are not part of the results.

## Limits stated in advance
The person is a script I wrote: its frames and the five kinds of mess are my guess of what messy answers look like, not data from people. The fault rates are round numbers. 42 tasks, 6 per policy and 2 repeats: small effects and per-policy effects are invisible. The model is one LoRA trained on home vocabulary. The simulator's own faults (a dropped object) fail some episodes in every arm. Step-3 answers are English only. Options were tuned on the home and earlier tasks, not on these.
