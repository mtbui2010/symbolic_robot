# NOT PLANNED: moving the sibling simulator's symbolic mode onto the core (gap list kept for reference)

Decision (2026-11-12): this repo is for benchmark runs only; the live symbolic mode stays in the sibling simulator's repository. The list below is only a reference if that changes.

This file names a private project on purpose (it is the plan for it); delete it before publishing the repository. Observed on the uncommitted work in `kcare_sim/symbolic/` (modules rng, profile, outcomes, layout, world, robot, perceive, manip, skills, sim_command, site, serve; 2,872 lines with tests). That repository was not modified.

## Already the same design (reused, nothing to do)
* Per-call 16-slot draws keyed by (seed, skill, canonical arguments, n-th call): `symbolic_robot.rng.CallDraws` (copied design; `callback` keys `node, wait, log_fn` are dropped from the key in both).
* Profile entries `{kind, value, source, note}` with a required source, `ideal` = real with probabilities 0, `Profile.get/uniform`.
* `sim_command` ops state / truth / reset / load / move_object / spawn, stub node with `mobile_pose`, `sim_world`, `sim_command`, forgetting the robot's memory files on a new world, ENV and MAP written by the launcher, speedup pacing with a cap.

## Gaps: what the core does not have yet (concrete)
1. **Result shape.** kcare's `Result` has `dur` (core: `duration_s`), a `.fail(code, msg, dur, injected, event)` helper, `to_legacy()` without `msg` when empty and `code` only on failure (core: always `msg`). Add the helper and an alias; decide the legacy shape per pack (the factory pack's adapter reads the core shape).
2. **Outcome helpers.** `split_code`, `failed(profile, key, clutter, u_fail, sticky, retry_key, cls)`, the slot enum `U` and the failure-code constants live in `outcomes.py`. The core now has `Profile.choose/by/uniform` (this step); the slot enum, the code constants and the sticky/retry rule are still one robot's. Move the code constants (robot_agent's FailureCode values) to a core module and the slot enum to the domain.
3. **Profile kinds.** Real profile has kinds `prob, prob_map, split, range, range_s, duration_s, distance_m, speed_mps`. The core knows `prob, prob_map` (zeroed in ideal), `split, range, number, map` (kept); `range_s, duration_s, distance_m, speed_mps` load fine (unknown kinds are kept) but are not validated. Its ideal file keeps the retry-recovery probabilities (`move.p_retry_clears_blocked`, `pick.p_retry_success`, `open.p_retry_success`, `close.p_retry_success`, `perception.p_clear_on_wait`; 5 of 37 keys): they need `ideal: keep` in the migrated YAML (supported now). Its ideal file differs from real in exactly 17 keys, all kinds prob/prob_map: derivation reproduces that once the 5 keys are flagged.
4. **Sticky device faults.** `FaultState(code, since, clears_on, p_clear)` per device (base, arm, camera, lift, head) and per path (`path:<target>`), persistent hardware faults, faults that clear on a wait of simulated time, retries that clear with a probability. The core has no fault-state store; the factory keeps its own `persistent` plan. A generic `FaultStore` (device -> state, clears_on never|retry|wait) belongs in the core only when a second domain needs it (the factory could then drop its own).
5. **Cancellation and busy state.** kcare's robot takes a `cancel()` callback (robot_agent's `run_control.cancel_requested`) and checks it before each call and during pacing; `busy`, an RLock around every call. The core's `SimClock.pace` accepts `cancel`, the live backend has `busy` and a lock, but the server does not pass robot_agent's cancel flag in (that import belongs in `server.py`). Gap: wire `cancel` in the glue.
6. **Display pose.** kcare replays only straight base motion and shows `None` when idle; the core live backend follows a domain route (`path()`) and keeps the last pose. For a kcare domain `path()` returns straight segments (nothing to add).
7. **Layout and objects.** `layout.py` reads the sim's `house_layout.yaml` (spots with centre, depth, width, front yaw, height; rooms; bounds; start), parses the object list of a sim script with `ast`, and checks it against the layout; `objects.yaml` is generated. Core `layout()` has places, regions, doors, labels only: no `spots` geometry (needed for the `surfaces` of the MAP group and for `move_object` by point on a surface rectangle: the core uses the nearest place within 1.2 m instead), no per-place `clutter`, `height`, `container_type`, `default_mode`. Add optional keys to the layout dict (`surfaces`, `bounds`) and let the domain pass them through; the core must not interpret them.
8. **Scenes.** `sim_command` ops `apply`, `save`, `delete`, scene files read from the sim's scene folder, the `scene`/`dirty`/`scene_def` fields, `skipped` list, furniture edits. The core's `state` returns the shape of the dashboard Sim bar but with `scene` = the world name, `dirty` false, no `furniture`, no scene storage; `load` switches the world. Add domain hooks `op_apply/op_save/op_delete` (default: not supported) and a scenes folder in the run dir.
9. **Object geometry.** objects carry `pos`, `yaw_deg`, `lying`, `ycb`, `room` and a `surface` offset; `move_object` accepts `x, y, yaw_deg`. The core `view()` objects carry `cls, at` and whatever the domain adds; `state` fills `pos` from the place. A domain that has positions should return them in `view()` (nothing to change in the core).
10. **Skill table.** Its skills keep the sibling robot's names and result shapes (`isdone`, `ins`, `pose`) and are installed over that robot's own skill table (`SKILL_CONFIGS` of its package), so its non-simulated skills (ask, reply, wait ...) stay. The core's `server.skill_table` adds only the launcher skills and dialogue skills over the pack's table; installing a domain's symbolic bodies over an external pack's table needs a hook (`BaseDomain.skill_overrides() -> {name: (module, func)}`, default empty).
11. **Site and connections.** `site.py` loads the sibling pack's config files as data (skill_configs_override.json: MOBILE_CONFIGS, FIND_CONFIGS, HRI_CONFIGS ...), copies `buttons.json`, builds ENV with the sim's own `build_env` and the MAP with `surfaces`, `rotate`, `lift` and `home` frames. The core writes `connections.json` and MAP (`image`, `places`, `pose`, `goal`, `sim`) only. Add a domain hook `site_files(run_dir)` and let `mapview.map_config` take extra keys from the domain (`rotate`, `lift`, `surfaces`, `origin`).
12. **Planner environment.** Its launcher sets ten planner options by default (ask_source with reask / room / clarify / near, input pivot both, translate retry, route weight 0.3); the home and factory domains declare theirs through `planner_env()`: the migrated domain declares the same dict. A second connection entry (speech-to-text) is already seeded by the core.
13. **Dependency check and help text.** `serve.check_deps()` and `--check` print how to point to the missing packages; the core's CLI only reports a failure to import. Add `python -m symbolic_robot run --check`.
14. **Pose agent stamps.** `rev_time` / `rev_data` on its pose agent (read by the sibling adapter's pose check). The core agent returns the snapshot only; add the two properties through a domain hook if the adapter needs them.
15. **Tests.** Its 4 test files (engine, sim_command, statistics, world; 5 + ... tests with a conftest that builds the ENV from sim scripts) test the sibling robot's rules; they move with the domain. The statistical test style (frequency within standard errors) is already in `tests/test_factory.py`.

## Order suggested
(1) result helper and failure-code constants; (2) layout passthrough keys and `skill_overrides` / `site_files` hooks; (3) scenes ops; (4) the domain itself (layout, world, skills, profiles) as `symbolic_robot/domains/<name>/` with its pack left in the sibling package; (5) fault store when a second domain wants it; (6) replay parity (record the sibling symbolic runs, replay them in the domain, as done for the factory).
