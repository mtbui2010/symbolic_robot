# Task data and its generation

!!! abstract "In this page"
    What the household task data is, where it lives, how it is loaded, how it is generated (in outline), and
    under which licence it may be used. This is an overview page. **It reproduces none of the data**: no
    task text in any language, no goals, no samples, no counts per split except the size of the dev split.
    The task data is research-only licensed in part; read the licence section before you use or copy it. A later
    part of this site goes deeper into generation.

## At a glance

| | |
|---|---|
| **What** | the household benchmark's tasks: one JSON record per task, in three split files |
| **Where** | `bench/suites/home/data/` (`tasks/`, `llm_cache/`, `pools/`, `quality/`, `label_policy.yaml`) |

| **Licence** | mixed; part is research-only. See below |
| **Tests** | `tests/home/bench/test_licence.py` (not run for this page) |

## What a task is

A **task** is one request that a person makes to the household robot, together with everything the judge needs
to score the episode: the house it happens in, the starting state, the goal in the simulator's own goal
language, labels, and what the simulated person will say. The same record has the request in English and in
Korean. See [Benchmark protocol](../learn/benchmark-protocol.md) for how a task becomes an episode.

`Task` is a frozen dataclass in [`tasks.py:14-47`](https://github.com/mtbui2010/symbolic_robot/blob/a5cc7a4943aa/bench/suites/home/tasks.py#L14-L47).
Its fields, in groups (the names are the schema; there are no values here):

| Group | Fields |
|---|---|
| Identity | `id`, `split`, `template_id`, `source` |
| The request | `text` (one entry per language), `length_words` |
| World | `house`, `seed_state`, `activity_source` |
| What counts as success | `goal`, `subtasks`, `n_subtasks`, `structure`, `order`, `mixed_kind`, `expected` |
| Labels | `kind` (for example a clarify or a refuse task), `capability`, `ambiguity`, `refuse_reason`, `hazards` |
| The simulated person | `user` |
| Provenance of the wording | `source_by_lang` (template or LLM paraphrase, per language), `paraphrase_model` (per language) |
| Free-form | `meta` |

Which fields a planner may see is not a data question: it is the `privileged` rule on the
[planner interface page](planner-interface.md#the-contract). Ordinary planners get the request text, not the goal.

## Where it lives and how it loads

| Path | What it holds |
|---|---|
| `bench/suites/home/data/tasks/{train,dev,test}.jsonl` | the three splits, one record per line |
| `bench/suites/home/data/label_policy.yaml` | the policy for the labels |
| `bench/suites/home/data/llm_cache/` | cached LLM responses used for paraphrasing and its quality checks |
| `bench/suites/home/data/pools/`, `data/quality/` | extra task pools, made like the splits but kept apart from them, and generated quality reports |

The dev split has **1,000** tasks (`wc -l` of `dev.jsonl` at the pinned commit). This page gives no other count.

`tasks.py` reads a split with `read_records`, builds `Task` objects once (`lru_cache`) and returns them in file
order. A task id carries its split, and `task_by_id` uses that.

Two guards protect the data:

- **The test split is closed on the front end.** `python -m bench run --domain home --suite run ...` refuses
  `--split test` with "the test split is not run through this front end". Current behaviour at this commit:
  the household CLI's own `run` command does not repeat that check; only the front end, `understand-eval`
  and `tasks-file` refuse the test split. Treat the test split as held out whichever entry you use.
- **A stale task file is refused.** `run` accepts `--tasks FILE`, but when a record has the id of a packaged
  train or dev task and different content, the run stops unless you pass `--allow-stale`. Such a file would
  measure an old data version.

## How it is generated (outline)

The generator is `python -m bench.suites.home.data <command>`. Its commands, in the order of use:

| Command | What it does |
|---|---|
| `generate` | build the template tasks and write the three split files |
| `paraphrase` | add LLM paraphrases in English and Korean; cached and resumable; needs a local LLM server |
| `resplit` | make the final split by task identity, so no goal or near-duplicate text sits in two splits |
| `validate` | the dataset checks (`--strict` turns warnings into failures) |
| `stats` | counts per label |
| `realism` | realism rules, with a report in `quality/` |
| `quality` | paraphrase and back-translation quality report (needs the LLM for new back-translations) |
| `delivery`, `kofix`, `tellfix` | deterministic repairs of delivery wording, Korean text and a re-render |
| `datasheet` | rewrite the datasheet from the shipped quality reports (no LLM) |

The modules in `gen/` (for example `sample`, `families`, `compound`, `paraphrase`, `resplit`, `validate`,
`oracle_check`) implement these. The validator checks each task against the household oracle (`oracle_check`, validator rule 5):
the `oracle` planner runs it in the `ideal` profile with seed 0. The English and Korean wording starts from templates;
an LLM then paraphrases a share of the records, and the record keeps which of the two produced each language
(`source_by_lang`, `paraphrase_model`). That field matters for the licence below.

None of this was run for this page: generation needs a local LLM server, and the data is not reproduced here.
A later part goes through the generator.

## Licence

!!! warning "Research-only in part"
    The task data is not under one licence. Read `bench/suites/home/LICENSE-DATA` and
    `bench/suites/home/NOTICE` before you use, copy or redistribute any of it.

The repository's README states the split between the parts (the "Licences" section):

| Part | Licence |
|---|---|
| The English texts, the Korean templates, the goals and the labels | Apache-2.0 |
| The Korean text written by a third-party model (EXAONE 3.5) and the cache rows built from it | **not** Apache-2.0: research use only, no commercial use, and no use of it to train or improve other models |
| The author's selection, filtering and labels attached to that part | CC BY-NC 4.0 |
| The benchmark code | Apache-2.0 |

For a use outside those terms, the data files say to use the Korean template wording instead of the
model-written Korean, which is Apache-2.0. The licence texts name the exact fields and the number of records
affected; this page does not repeat them. If you want to train a model, do not train on the model-written
Korean text.

This site follows the same rule for itself: it quotes no task text and no per-task rows. Where it
shows a number about the data it is an aggregate, with its source. The licences of the whole repository are in
[Versions and licences](../reference/versions-and-licences.md).

## Edge cases and failure modes

| Symptom | Cause | Result |
|---|---|---|
| `--split test` refused | the front end blocks the test split | `refused: the test split is not run through this front end` |
| `--tasks FILE` refused | records with packaged ids but other content | stop, unless `--allow-stale` |
| `paraphrase` or `quality` cannot run | they need a local LLM server | use `--offline` to replay from the cache |
| report commands write elsewhere | an installed (non-editable) package has no source checkout | they write to a separate quality folder and do not write docs |

## How it is verified

`tests/home/bench/test_licence.py` reads the records and checks that the licence statements match them: that the
Korean part and the training warning are in `LICENSE-DATA`, that the count of affected records in the licence
equals the count in the data, and that the benchmark's own README, the NOTICE and the datasheet carry the same warning. It
needs the full data, including the test split. I did not run it for this page.
